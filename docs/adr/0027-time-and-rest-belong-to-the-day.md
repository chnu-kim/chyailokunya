# ADR-0027: 방송 시각과 휴방은 항목이 아니라 하루의 속성이다

- 상태: Accepted
- 날짜: 2026-07-29

## 맥락

이슈 #56 **결정 8**은 "하루 여러 항목 · 시각은 선택"이었고, 근거는 `"오후 저챗 + 밤 게임"`
편성을 그대로 담기 위해서였다. 그래서 `schedule_entries.start_time` 이 항목마다 붙었다.

2026-07-29 라이브 검수에서 그 근거가 **실재하지 않는 것으로 확인됐다** — 하루에 방송은
하나이고, 한 방송에서 게임을 여러 개 하는 것이 실제 모양이다. 그러면 항목마다 시각을 두는
구조는 같은 값을 하루 안에서 반복해 적게 만들고, 서로 다른 값이 들어갈 자리를 연다.

같은 검수에서 두 번째 요구가 나왔다: **휴방**. 지금은 "아직 안 정한 날"과 "쉬기로 정한 날"이
둘 다 `—` 로 보여 팬이 구분할 수 없다. 둘은 다른 사실이고, 둘 다 **하루**에 달린 사실이다.

## 결정

**하루를 속성을 갖는 개체로 승격한다.** `schedule_days` 테이블을 신설해 방송 시작 시각
(`start_time`)과 휴방(`rest`)을 담고, `schedule_entries.start_time` 을 드롭한다. 항목은
"그 방송에서 무엇을 하는가"의 목록이 된다.

**"빈 주"의 정의를 바꾼다** — 항목 0 **그리고** 휴방 0 일 때만 빈 주다. 7일을 전부 휴방으로
정한 주는 항목이 0개지만 관리자가 짠 결과이고 발행할 만하다.

## 근거

- **개념이 이름과 자리를 정한다.** 시각과 휴방은 항목의 성질이 아니라 하루의 성질이다. 항목에
  두면 하루에 항목이 둘일 때 어느 값이 참인지가 데이터로는 결정되지 않는다.
- **행이 없는 것 = 기본값.** `start_time NULL` + `rest 0` 은 행이 아예 없는 것과 같은 뜻이고,
  서비스는 기본값인 날의 행을 안 만든다. ADR-0024 가 #64 에서 비싸게 배운 규율의 반대 방향
  적용이다 — 거기선 "부재를 도메인 상태로 쓰면 그 행이 다른 이유로 필요해질 때 겸직이 터진다"를
  배웠고, 여기선 **기본값이 부재와 같은 뜻이 되게** 컬럼을 잡아 그 함정 자체를 없앤다.
- **"빈 주" 재정의는 화면과 서버를 일치시킨다.** 안 바꾸면 화면은 7일이 다 정해진 주를
  보여주는데 발행만 서버에서 거절당한다 — 이 저장소가 반복해 밟은 "게이트는 초록인데 라이브에서
  막힌다" 모양이다.

## 기각한 대안

- **하루 시각을 기본값으로 두고 항목이 덮게 한다** — 마이그레이션이 훨씬 작고(컬럼 추가만)
  데이터 손실이 0 이다. 사용자에게 두 안을 실제 표기로 보여 물었고, **하루에 방송이 하나뿐**
  이라 override 가 표현할 대상이 없다는 답을 받았다. 쓰지 않을 자유도를 남기면 두 자리가
  같은 사실을 말하게 되고, 어긋났을 때 어느 쪽이 참인지 규칙이 또 필요해진다.
- **휴방을 `schedule_entries` 의 특수 항목으로** — 제목이 "휴방"인 항목을 넣는 식. 문자열이
  도메인 상태를 겸직하고, 그 항목이 게임 보드의 플레이 날짜 유도에 섞인다.
- **휴방을 주 메타에 7일치 컬럼으로** — `rest_mon`…`rest_sun`. 캘린더(월 단위)로 넓힐 때
  그대로 무너진다.
- **휴방과 항목의 공존을 DB CHECK 로 금지** — 둘이 다른 테이블이라 SQLite 제약이 못 닿는다.
  **표시에서 휴방이 이기게** 하고 저장은 그대로 둔다 — 실수로 켰다 꺼면 항목이 돌아온다.
  지우는 쪽을 택하면 그 실수가 복구 불가가 된다. 알고 수용한 한계다.
- **이관 시 손실을 조용히 감수** — 초판은 `GROUP BY … MIN(start_time)` 으로 접었다. 하루에 서로
  다른 시각이 있는 날이 프로덕션에 하나라도 있으면 **되돌릴 수 없이** 값이 사라지고, 배포는
  성공한 채라 복구가 백업 뒤지기가 된다. 대신 `DISTINCT` 로 시각마다 한 행씩 넣어
  `scheduled_date` UNIQUE 가 그 경우를 **fail-closed** 로 만든다 — 손실이 없을 때만 통과하고,
  있으면 배포가 멈춰 사람이 먼저 결정한다. 별도 가드 구문 없이 제약 하나로 계약이 선다.
- **게임 폼이 휴방인 날에 날짜를 쓰면 자동으로 휴방을 푼다** — 그러면 게임 폼의 저장이
  **주간표를 바꾼다**(팬이 보는 화면에서 "휴방"이 사라진다). 게임 폼은 그 권한을 주장한 적이
  없다. 대신 `PlayDateOnRestDay` 로 거절하고 /schedule 로 가리킨다 — 통과시키면 쓰기는 성공하는데
  보드가 그 날짜를 안 세, 관리자가 넣은 값이 화면에서 사라진 것처럼 보인다(AGENTS 의 "보드를
  안 바꾸는 쓰기는 성공 신호가 하나도 없다"와 같은 자리).

## 결과

**(+)** 시각이 한 자리에만 있어 어긋날 자리가 사라졌다. 휴방이 명시 상태가 되어 팬이 "아직
미정"과 "쉰다"를 구분한다. 카드·읽기 화면이 시각을 요일 옆에 한 번만 그려 반복이 사라졌다.

**(−)** 하루에 시각이 둘 이상인 날이 있으면 **마이그레이션이 죽는다**(fail-closed). 배포가 멈추는
비용을 지불하는 대신 조용한 손실을 없앴다 — 그런 날이 실제로 있으면 사람이 먼저 결정한다.
공유 PNG 의 그림이 바뀐다(요일 옆 시각 배지 + 휴방 표기).

**(−)** 게임 폼이 휴방인 날짜를 거절한다. 관리자는 /schedule 에서 휴방을 먼저 풀어야 한다 —
한 번에 못 하는 마찰이지만, 게임 폼이 주간표를 조용히 고치는 것보다 낫다.

**두 쓰기 경로가 같은 조합을 다르게 대한다 — 의도된 비대칭이다.** `saveWeek` 은 `rest=1` + 항목
공존을 **허용**하고(결정 5, 표시에서만 가린다), `games.add`·`games.update` 는 **거절**한다. 같은
데이터 조합인데 한쪽은 되고 한쪽은 안 되는 이유는 두 화면이 주장하는 바가 달라서다 —
/schedule 은 일정의 주인이라 "항목이 있는 날을 쉬기로 한다"가 정당한 편집이고, 게임 폼은
"이 게임을 그날 했다"를 주장하는데 그건 휴방과 모순된다. 적지 않으면 다음 사람이 이걸 버그로
보고 한쪽을 "고친다".

**(−)** 게임 폼의 휴방 검사는 **읽고→쓰기**라 동시 편집에 창이 있다(적대적 리뷰 4라운드).
다른 관리자가 그 사이 같은 날짜를 휴방으로 바꾸면 항목이 만들어지고 보드가 그걸 안 센다.
수용한다: 같은 날짜를 **수 ms 창**에 겹쳐야 하고, 결과가 파괴적이지 않으며(휴방을 풀면 날짜가
그대로 돌아온다) 같은 함수가 이미 같은 급의 창을 문서화한 채 수용하고 있다. 제안 쿼터가
트리거로 간 것(0010)과는 종류가 다르다 — 그건 상한이 **버스트 크기만큼** 뚫리고 자기 치유가
없으며 로그인만 하면 닿는 경로였다.

**(−)** 같은 규칙이 세 곳에 산다 — 서버 `weekHasContent`, core `draftHasContent`, 그리고
정렬 규칙이 `getWeekForEdit` 의 `ORDER BY` 와 `entriesForDate` 로 갈려 있다. core 는 features 를
못 보므로(레이어 경계) 합칠 수 없다. **한쪽을 고치면 반드시 다른 쪽도 고친다** — 각 파일 주석이
서로를 가리킨다.

**후속:** 마이그레이션 0011 의 회귀는 `e2e/migration-0011.spec.ts` 가 `node:sqlite` 로 트랜잭션
안에서 재생한다(0007·0008 과 같은 자리). 팬아트 자리는 별도 작업이다(이슈 #117).
