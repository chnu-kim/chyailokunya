# ADR-0028: 팬아트 바이트는 R2 에 두고 Worker 가 프록시한다

- 상태: Accepted
- 날짜: 2026-07-30

## 맥락

이슈 #117 작업순서 7(그 주에 걸어 둘 팬아트)의 첫 판은 **외부 URL** 이었다 — 관리자가 트위터·
치지직 등에 올라간 그림의 주소를 붙여넣고 읽기 화면이 그걸 `<img src>` 로 그대로 건다(PR #119).
파일을 안 가지니 스토리지가 필요 없고, 그 편의가 유일한 근거였다.

그 PR 은 닫혔다. 외부 주소를 `<img src>` 에 걸면 **그 페이지를 연 방문자의 IP·User-Agent·시각·
요청량이 우리가 모르는 서버로 간다.** `referrerPolicy="no-referrer"` 는 Referer 헤더(어느
페이지에서 왔나)만 가릴 뿐 요청 자체를 막지 못한다 — 브라우저가 그 호스트에 직접 연결하기
때문이다. 팬 사이트 방문자를 제3자에게 노출시키는 것이라, 관리자가 주소 하나 붙여넣는 편의와
바꿀 값이 아니다(2026-07-30 사용자 결정).

같은 결정이 하나를 더 푼다. 지금 주간표 PNG 카드에는 팬아트를 **못 싣는다** — `html-to-image`
가 이미지를 fetch 해 dataURL 로 인라인하는데(`resourceToDataURL`), CORS 헤더가 없는 외부
이미지는 실패를 빈 src 로 삼켜 캡처가 깨진다(실측). same-origin 바이트면 그 벽이 사라진다.

제약 두 가지가 설계를 좁힌다:

- **Workers 무료 플랜의 요청당 CPU 10ms.** 이 저장소는 여기서 프로덕션 인시던트를 한 번 냈다 —
  `/api/og/schedule` 이 Satori/resvg 로 PNG 를 렌더하다 한도를 넘겨 isolate 가 죽고, 같은
  isolate 를 타던 무관한 요청까지 연쇄로 실패했다(Error 1102, 2026-07-27). 게이트 8종 중
  어느 것도 이걸 못 잡는다.
- **서빙 origin 은 apex 하나뿐이다**(AGENTS). 앱이 절대 URL 을 `chyailokunya.com` 하나에
  고정하고, `AUTH_URL` Origin 검증이 그 값과 정확히 일치해야 쓰기가 통과한다(ADR-0017).

## 결정

**R2 버킷을 하나 들여 팬아트 바이트를 우리가 보관하고, Worker 라우트가 그걸 프록시한다.**

세 가지를 함께 못박는다:

1. **DB 엔 URL 이 아니라 객체 키만 담는다** — `schedule_weeks.fanart_image_key` 는
   `<uuid>.<ext>` 한 조각이고, R2 prefix(`fanart/`)와 서빙 경로(`/api/fanart/…`)는 코드가
   조립한다.
2. **public bucket 을 열지 않는다** — 읽기도 우리 Worker 를 거친다.
3. **요청 경로에서 이미지를 만지지 않는다** — 업로드는 앞 12바이트만 보고(매직 바이트),
   서빙은 R2 응답 본문을 스트림 그대로 흘린다. 리사이즈·포맷 변환·디코드는 어느 경로에도 없다.

## 근거

- **유출 경로를 타입으로 닫는다.** 컬럼이 URL 이면 값이 외부 호스트를 가리키는 행을 **아무것도
  막지 못한다** — 검증을 넣어도 그건 코드의 약속일 뿐이고, 이 이슈가 닫으려는 구멍이 정확히
  거기다. 키는 호스트를 표현할 문법 자체가 없다. "URL 을 어디서 얻는가만 바뀐다"로 접근하면
  같은 구멍을 다른 이름으로 남긴다.
- **public bucket 은 두 번째 origin 이다.** `*.r2.dev` 를 열면 AGENTS 의 "apex 하나" 원칙과
  정면으로 부딪히고, 그 주소는 우리 캐시·헤더·수명 정책 밖에 있다. Worker 프록시면 접근 정책이
  코드에 있고 나중에 바꿀 수 있다.
- **프록시는 CPU 를 안 쓴다.** `object.body` 는 `ReadableStream` 이라 Worker 가 바이트를 읽지
  않고 그대로 반환한다 — og:image 를 죽인 것은 프록시가 아니라 **렌더**였다. 그 차이가 이
  설계의 전제이므로, 서빙 경로에 변환을 얹는 순간 같은 인시던트로 돌아간다.
- **확장자와 Content-Type 은 클라이언트의 주장이다.** 둘 다 위조 가능하므로 실제 바이트 앞의
  시그니처로 png/jpeg/webp 를 확인한다. 이건 디코드가 아니라 12바이트 비교라 CPU 가 사실상 0 이다.
- **키가 유일해도 캐시는 짧게 잡는다.** 파일명이 UUID 라 같은 주소의 *내용*은 안 바뀌므로
  `immutable` 이 맞아 보이는데, 그 판단은 이 자원이 **삭제된다**는 사실을 빠뜨린 것이다 —
  잘못 올렸거나 내려 달라는 요청을 받아 지워도 한 번 열린 URL 이 1년간 캐시에서 서빙된다.
  Cache API 의 `delete` 는 그 요청을 받은 콜로케이션만 비우므로 온전한 해결이 아니고, "지웠다"고
  믿게 만드는 부분 해결이 더 위험하다. 그래서 `max-age=3600` · immutable 없음으로 두고 만료 뒤엔
  ETag 재검증(304)에 맡긴다. 엣지에 앉히는 건 `caches.default` 로 직접 한다 — 헤더만으론
  Worker 응답이 엣지 캐시에 안 들어간다(AGENTS 지뢰).

## 기각한 대안

- **외부 URL 유지(PR #119)** — 이 ADR 이 대체하는 대상이다. 방문자 IP 유출이 결정적이고,
  덤으로 PNG 카드에 못 싣는다.
- **DB 에 우리 origin 의 절대 URL 을 저장** — 마이그레이션이 가장 작고 화면 코드가 안 바뀐다.
  그런데 외부 호스트를 가리키는 행을 막을 수단이 여전히 없고(위 근거), origin 이 바뀌면 모든
  행을 고쳐야 한다. 값이 배포 환경을 알아야 할 이유가 없다.
- **R2 public bucket / `r2.dev` 직접 노출** — 두 번째 origin. 위 근거.
- **Cloudflare Images** — 리사이즈·포맷 협상을 대신 해 주지만 유료이고, 팬아트 한 주 한 장에
  외부 의존을 하나 더 들일 근거가 안 된다(ADR-0010 의 JIT).
- **업로드 시 서버에서 리사이즈·webp 변환** — 저장 용량과 카드 인라인 비용이 줄지만, 그건
  이미지를 **디코드해 다시 인코드**하는 일이라 정확히 og:image 를 죽인 종류의 CPU 다. 필요해지면
  브라우저에서(관리자 기기의 CPU 로) 줄여 올린다.
- **D1 에 BLOB 으로 저장** — 스토리지를 안 늘려도 된다. 그러나 D1 은 행 단위로 읽는 관계형
  저장소라 수 MB BLOB 이 주 메타 조회에 통째로 딸려 오고, 바이트를 스트림으로 흘릴 수도 없다.
- **저장과 옛 객체 삭제를 원자적으로** — D1 엔 대화형 트랜잭션이 없다(AGENTS). 업로드→저장→삭제
  세 단계 중간이 끊기면 고아 객체(비용만 든다) 또는 dangling key(그림이 깨진다) 중 하나가 남는데,
  **고아 쪽으로 실패하게** 설계를 고정한다.

## 결과

**(+)** 방문자의 IP·UA 가 우리 origin 밖으로 안 나간다. 그림의 수명·삭제·접근 정책이 우리 손에
들어온다.

**(+)** same-origin 바이트라 PNG 공유 카드에 실을 수 있는 길이 열렸다. **이번엔 안 싣는다** —
공유될 그림 자체가 바뀌는 결정이라 카드 레이아웃·`week-card.test.tsx`·PNG e2e 를 함께 다루는
별도 작업이다.

**(−)** 저장소를 하나 더 운영한다. Cloudflare 계정에서 R2 를 활성화해야 배포가 성립한다
(무료 티어 10GB · Class A 1M/월 안에서 도는 규모지만, 활성화 자체가 계정 작업이다).

**(−)** 고아 객체가 쌓인다. 업로드 뒤 저장 없이 떠나거나 배포·요청이 중간에 끊기면 아무 행도
가리키지 않는 객체가 남는다. 위 기각 항목대로 **알고 고른 실패 방향**이다 — 정리가 필요해지면
DB 를 정본으로 하는 별도 작업으로 훑는다.

**(−)** 업로드 상한(5MB)이 관리자에게 보인다. 원본이 큰 그림은 미리 줄여 올려야 한다 — 서버
변환을 안 하기로 한 대가다.

**(−)** 엣지 캐시가 비면 첫 요청이 R2 를 한 번 왕복한다. CPU 가 아니라 대기 시간이라 10ms 한도와
무관하고, 그 뒤 1시간은 캐시가 받는다.

**(−)** 지운 팬아트가 **최대 1시간** 옛 URL 로 계속 보인다. 즉시 사라지게 하려면 캐시를 아예
포기해야 하는데, 팬아트 URL 은 화면에서 사라진 뒤 그 주소를 이미 아는 사람만 두드릴 수 있어
그 값이 캐시 이득보다 크지 않다고 봤다. 즉시성이 실제로 요구되면 max-age 를 더 줄인다.

**(−)** 로컬·e2e 는 Miniflare 의 R2 시뮬레이션 위에서 돈다. D1 과 같은 구조라 새 함정은 아니지만,
**프로덕션 R2 의 동작을 로컬 게이트가 증명하지는 않는다**(이 저장소가 반복해 밟은 자리 —
`next build` 가 배포 계약을, 로컬 workerd 가 CPU 정책을 증명하지 않는 것과 같다).
