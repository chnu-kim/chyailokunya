# ADR-0030: 팬아트 치수는 R2 객체에 묶고, 표시 상한은 CSS 가 건다

- 상태: Accepted
- 날짜: 2026-07-30

[ADR-0028](./0028-fanart-bytes-in-r2.md)의 "DB 엔 객체 키만 담는다"를 **확장한다** — 키 옆에
폭·높이 두 컬럼이 붙는다. `public bucket 을 안 연다` 는 그대로이고, `요청 경로에서 이미지를
만지지 않는다` 는 **해석이 하나 분명해진다**: 그 결정이 막은 것은 디코드·재인코딩이고, 규격이
파일 앞머리에 못박은 정수를 읽는 **헤더 파싱은 매직 바이트 판정과 같은 급**이라 여기 들어온다.

## 맥락

읽기 화면(`/schedule`)의 팬아트는 목록 아래에 사진지(`.polaroid`)로 서고 `loading="lazy"` 다.
그림이 로드되는 순간 그 아래(푸터)가 밀린다 — `<img>` 에 `width`/`height` 가 없으면 브라우저가
비율을 몰라 자리를 못 비우기 때문이다. AGENTS 는 이 사이트가 `next/image` 없이 평범한 `<img>` 와
width/height 로 **CLS 만 막는다**고 이미 정해 뒀는데, 팬아트는 그 수치를 어디에서도 얻을 수
없었다:

- **서빙 응답에 치수가 없다.** ADR-0028 이 R2 스트림을 그대로 흘리기로 했으므로(Worker 가
  바이트를 안 만진다) 폭·높이를 아는 코드가 서빙 경로에 없다.
- **키에서 유도할 수도 없다.** 저장되는 값은 `<uuid>.<ext>` 한 조각이다.
- 팬아트는 세로로 긴 일러스트가 흔해 비율 편차가 크다 — 고정 `aspect-ratio` 로 뭉개면 사진지
  안에 작은 그림이 떠 폴라로이드 은유가 깨진다.

그리고 **바이트 상한(5MB)이 못 막는 것이 둘 더 있다**(적대적 리뷰가 두 축을 각각 냈다):

- **픽셀 폭탄** — 단색 20000×20000 PNG 는 압축 상태로 수 KB 인데 디코드하면 픽셀당 4바이트로
  펼쳐져 1.6GB 다. 발행된 주를 여는 **모든 방문자의 탭이 죽는다.**
- **극단 비율** — 1200×20000 은 픽셀 예산 안이고 한 변 상한 안인데, 420px 폭에서 `height:auto`
  면 높이가 7000px 이 되어 그 아래 콘텐츠를 통째로 밀어낸다. 위조가 아니라 **평범한 관리자
  업로드**로 도달한다.

## 결정

**업로드 라우트가 형식 헤더에서 폭·높이를 읽어 두 상한으로 거절하고, 통과한 치수를 R2 객체
메타에 묶는다. 저장 경로가 그 메타에서 읽어 컬럼에 담는다 — 화면은 치수를 만지지 않는다. 렌더
높이는 CSS 가 제한한다.**

넷을 함께 못박는다:

1. **치수는 클라이언트를 거치지 않는다.** `POST /api/fanart` 는 `{ key }` 만 돌려주고, 치수는
   객체의 `customMetadata` 에 있다. `saveWeek` 이 키를 확인하려 이미 부르는 `head` 응답에서 그
   값을 읽으므로 왕복이 늘지 않는다. 저장 입력(Zod)에는 치수 필드가 **아예 없다**.
2. **업로드가 통과시킨 치수는 저장도 통과한다** — 업로드 가드가 저장 경계(Zod)와 **같은 두
   상한**을 본다: 픽셀 예산 40MP · 한 변 20000. 헤더를 못 읽으면 거절한다(fail-closed).
3. **컬럼은 nullable 이고 항상 한 쌍이다.** 0013 이전에 걸린 그림은 치수가 없고, 읽기 화면은
   그때 속성을 안 달아 예약 없이 그린다. 반쪽 조합은 Zod·`nextFanart`·DB CHECK 가 세 층에서
   막는다.
4. **렌더 높이 상한은 CSS 에 둔다** — `.sched-fanart-card__img` 의 `max-height: min(720px, 80vh)`
   - `object-fit: contain`.

## 근거

- **헤더 읽기는 공짜다.** 바이트는 이미 `readCapped` 가 메모리에 올려 뒀고, 읽는 것은 PNG IHDR ·
  JPEG SOF · WebP VP8/VP8L/VP8X 의 정수 몇 개다. 화면이 대신 읽으면 `createImageBitmap` 으로
  **전체를 디코드**한다 — 예산 안(40MP)이어도 160MB 비트맵이라 픽셀 가드가 막으려던 것과 같은
  급의 할당이 관리자 탭에 생긴다(적대적 리뷰 5라운드).
- **그 값을 화면으로 되돌리지 않는다.** 응답에 실어 화면이 저장에 싣게 하면 **다시 클라이언트
  주장이 된다** — Zod 가 형식만 보므로 stale·위조 값이 그대로 컬럼에 들어가고, 불변식 2("입력은
  신뢰하지 않는다")가 이 필드에서만 빠진다(적대적 리뷰 9라운드). 객체에 묶으면 값이 키를 따라
  움직이고, 그 키는 이미 R2 존재 확인을 거친다. 5·9라운드가 같은 자리를 두 방향에서 짚었다:
  화면이 직접 디코드하는 것도, 서버 값을 에코하는 것도 아니다.
- **저하 경로가 사라진다.** 클라이언트가 읽던 판에서는 `createImageBitmap` 이 없거나 실패하면
  치수가 null 이 됐다 — 업로드는 성공하고 예약만 빠지는, **화면에 아무 신호 없는** 상태였다
  (개발 중 CRC 깨진 e2e 픽스처가 실제로 그 상태를 만들었고 D1 을 직접 봐야 원인이 나왔다).
  서버가 읽으면 성공 응답엔 치수가 항상 있다.
- **두 상한이 다른 것을 막는다.** 픽셀 예산은 **방문자 브라우저의 디코드 메모리**를, 한 변 상한은
  **저장 경계가 거는 값**을 지킨다. 함께 안 보면 계약이 갈린다: 20001×1 은 2만 화소라 예산을
  통과하는데 저장에서 BAD_REQUEST 로 죽어 **업로드는 성공하고 그림은 어디에도 못 걸린다.**
- **헤더를 못 읽으면 거절한다(fail-closed).** 통과시키면 폭탄 방어에 우회로가 생긴다. 매직
  바이트를 이미 지난 파일이므로 "그 형식이라고 주장하는데 헤더가 규격과 다르다"는 뜻이고, 그런
  파일은 브라우저도 못 그려 통과시켜도 그림이 안 뜬다.
- **극단 비율은 업로드가 아니라 표시가 막는다.** 이유가 둘이다. (1) 세로로 긴 일러스트는 **정당한
  팬아트다**(9:16 이 흔하다) — 거절하면 정상 콘텐츠를 막고, 문제는 그림이 아니라 이 화면이 그걸
  그리는 방식이다. (2) CSS 는 **모든 행을 덮는다** — 0013 이전 그림, 치수가 null 인 행, 위조된
  치수까지. 서버 가드는 새 업로드만 덮어 우회로가 남는다. CLS 도 안 깨진다: 브라우저가 상자를
  계산할 때 `max-height` 를 함께 보므로 예약과 렌더가 어긋나지 않는다.
- **키가 같으면 기존 값을 유지한다** — 치수는 키에 딸린 값이라 "키가 같은데 치수만 바뀌는" 정당한
  경로가 없다. 그래서 `head` 는 키가 바뀔 때만 부르고(비용 유지), 그때 읽은 메타가 새 치수가 된다.
  메타가 없거나 못 쓸 값인 객체(이 가드 이전에 올라간 것)는 치수 없이 저장돼 예약 없이 그려진다.
- **JPEG 은 상한이 **둘** 필요하다** — 세그먼트 수(64)와 **마커 앞 패딩**(16). 앞은 길이 0 으로
  오프셋이 안 늘어나는 무한 루프를 막고, 뒤는 5MB 를 전부 `0xff` 로 채운 파일이 **한 반복에서
  ~500만 회를 도는** 것을 막는다(세그먼트 예산은 그때까지 1 도 안 줄어든다 — GitHub codex 리뷰가
  이 자리를 잡았다). 요청 경로에서 도는 코드라 상한이 없으면 **방어 코드 자체가 10ms 한도를
  먹는다.** 같은 부류를 전수로 점검했다: EXIF IFD 순회(256) · APNG 청크 스캔(4096) · WebP(루프
  없음) — 상한 없는 자리는 이 패딩 하나뿐이었다.
- **JPEG 은 EXIF 회전도 봐야 한다**(plain 리뷰 6라운드). 브라우저는 `image-orientation: from-image`
  가 기본값이라 EXIF orientation 을 적용해 그리는데, SOF 가 적은 것은 **회전 전 픽셀 행렬**이다.
  5~8(90°/270° 계열)이면 표시 치수가 뒤바뀌므로 그대로 저장하면 예약 비율이 뒤집혀 **이 컬럼이
  막으려던 바로 그 시프트**가 난다 — 폰으로 찍어 올린 세로 그림이 그 부류이고 팬아트 맥락에서
  흔하다. IFD0 의 태그 0x0112 하나만 읽고(엔디안 두 경로 · 엔트리 순회 상한 256) 못 읽으면
  스왑하지 않는다(회전 정보 없는 JPEG 과 같은 취급).
- **애니메이션은 받지 않는다**(GitHub codex 리뷰 P2). APNG(`acTL`)와 애니메이션 WebP(VP8X 의
  ANIMATION 비트)가 통과하고 있었는데, 셋이 걸린다: gif 를 뺀 근거("팬아트 한 장")를 우회하고,
  **`<img>` 로 재생되는 애니메이션은 CSS 의 `prefers-reduced-motion` 가드가 못 막고**(접근성
  기준은 "새 애니메이션은 그 가드 안에"다), 픽셀 예산이 캔버스 한 장만 세므로 프레임 반복
  디코드를 안 센다. 판정도 헤더만 본다(청크 순회 상한 32 · IDAT 를 만나면 중단).
- **판정은 순수 함수다**(`readImageDimensions` · `isFanartSizeAcceptable`) — 경계값·형식별 파싱을
  단위 테스트가 본다(ADR-0029 의 "어느 층이 이걸 보나"). 라우트 테스트는 "거절이 실제 상태 코드로
  나오는가"만, e2e 는 "그 그림이 팬 화면에 뜨는가"만 본다.

## 기각한 대안

- **치수를 저장하지 않고 시프트를 감수** — 코드가 0 이다. 그런데 팬아트는 문서 마지막이 아니라
  푸터 위에 있어 로드 시점에 실제로 화면이 움직이고, AGENTS 가 이미 "CLS 만 막는다"를 이 사이트의
  이미지 규칙으로 정해 뒀다.
- **CSS `aspect-ratio` 고정(치수 없이)** — CSS 두 줄이고 계약 변경이 0 이다. 시프트는 사라지지만
  **모든** 세로 긴 일러스트가 좌우 여백을 얻어 "사진지 안의 작은 그림"이 된다. 지금 방식에서
  `contain` 은 상한에 닿는 극단 비율에서만 발동한다.
- **클라이언트가 파일에서 읽어 보낸다** — 이 PR 이 처음 구현한 방식이고 리뷰로 바꿨다. 서버 CPU 를
  안 쓴다는 장점이 있었지만, (1) 관리자 탭이 전체를 디코드하고 (2) 못 읽는 환경에서 치수가 조용히
  사라지고 (3) 어차피 픽셀 가드가 서버에서 같은 헤더를 읽고 있었다.
- **서버가 응답에 실어 주고 화면이 저장에 싣는다** — 두 번째로 구현한 방식이고 또 바꿨다. 디코드
  비용은 사라지지만 값이 화면을 왕복하면서 **다시 클라이언트 주장이 된다**: 저장 경계는 그것이 그
  키의 진짜 치수인지 알 방법이 없다. 객체 메타가 그 연결을 데이터로 만든다.
- **서버가 저장까지 대신한다**(업로드가 주 메타에 직접 쓴다) — 위조 여지가 없어진다. 그런데
  업로드는 "바이트만 맡는다"가 ADR-0028 의 결정이고, 그 키가 어느 주에 걸리는지는 `saveWeek` 의
  CAS 계약 안에 있어야 한다(발행 경계·revision). 업로드가 주를 알면 그 계약이 둘로 갈린다.
- **R2 `customMetadata` 에 치수를 넣고 읽기 화면이 조회** — DB 컬럼이 안 늘어난다. 그러나 서버
  컴포넌트가 그 주를 그릴 때마다 R2 왕복이 하나 붙고, 그 왕복은 D1 조회와 원자적이지도 않다.
- **업로드에서 극단 비율을 거절** — 위 근거의 (1)(2). 정당한 세로 그림을 막고, 이미 저장된 행을
  못 덮는다.

## 결과

**(+)** 발행된 주를 열 때 팬아트가 자리를 미리 차지해 푸터가 안 밀린다. 비율은 실제 그림 그대로다
(`width`/`height` 속성 + CSS `width:100%; height:auto` — CLS 를 막는 표준 조합).

**(+)** 픽셀 폭탄과 극단 비율이 각각 다른 층에서 막힌다 — 전자는 서버가 R2 에 넣기 전에, 후자는
CSS 가 렌더 시점에. 후자를 CSS 에 둔 덕에 **이미 저장된 행과 위조 치수까지** 덮인다.

**(+)** 관리자 탭이 이미지를 디코드하지 않는다. 업로드가 하는 일은 바이트 전송 하나다.

**(−)** 컬럼이 둘 늘고 마이그레이션 0013 이 생겼다. CHECK 를 건드려 테이블이 재생성되므로
0008·0012 와 같은 손편집 지뢰(생성물의 `INSERT … SELECT` 가 옛 테이블에서 새 컬럼을 읽는다)를
또 밟았고, `e2e/migration-0013.spec.ts` 가 그 손편집을 못박는다.

**(−)** 치수 없는 행이 존재한다(0013 이전에 걸린 그림). 그 주는 예약 없이 그려진다 — 기능이
깨지는 게 아니라 이 ADR 이전 상태로 돌아갈 뿐이고, CSS 상한은 그 행에도 그대로 걸린다.

**(−)** 우리가 헤더를 못 읽는 정상 파일은 거절된다(모르는 WebP 변종 등). 형식은 이미 매직
바이트로 셋으로 좁혀졌으므로 그 안에서 헤더가 규격과 다르면 깨진 파일일 가능성이 높다고 봤다.
새 변종이 실제로 막히면 그 파서를 더한다.

**(−)** R2 객체 메타가 계약이 됐다 — 업로드가 심는 키 이름(`w`·`h`)과 저장이 읽는 이름이 갈리면
치수가 조용히 사라진다(그림은 걸린다). 읽는 쪽이 파싱·검증을 함께 하고(`fanartSizeFromMetadata`),
라우트 테스트가 심는 값을 · 라우터 테스트가 읽는 값을 각각 못박는다.

**(−)** 브라우저가 디코드하는 과정을 **로컬 게이트가 증명하지 못한다.** 개발 중 e2e 픽스처의
PNG 가 IDAT CRC 가 깨진 판이라 브라우저가 디코드를 거부했는데(`InvalidStateError`) `file(1)` 은
헤더만 봐서 유효한 PNG 로 보고했다 — 저장은 성공하고 치수만 null 이 되는, **화면에 아무 신호도
없는 상태**였다(그 상태 자체는 이제 서버가 치수를 주므로 사라졌다). 픽스처를 손으로 인코딩하고
청크 CRC 를 검증해 고쳤다. 이미지 바이트를 다루는 테스트는 "형식이 맞아 보이는 조각"으로 대신할
수 없다.
